# Кейс: Оптимизация контент-стратегии и рефакторинг архитектуры базы данных блога

* **Цель проекта:** Выявить наиболее эффективные темы и форматы контента для разработки дальнейшей стратегии ведения блога.
* **Инструменты:** PostgreSQL, DBeaver.
* **Исходные данные:** Выборка из 25 постов за сентябрь 2026 года, собранная вручную в формате плоской таблицы Excel.

---

## Этап 1. Анализ гипотез и метрик эффективности (Сентябрь 2026)

### Запрос 1. Топ-темы по просмотрам в первую неделю после публикации
```sql
SELECT theme, ROUND(AVG(views_1week), 2) AS avg_views_1week
FROM blog_post_stat
WHERE post_date BETWEEN '2026-09-01' AND '2026-09-30'
GROUP BY theme
ORDER BY avg_views_1week DESC;
```
* **Вывод:** Больше всего просмотров за первую неделю набрали темы **AI, обзоры приложений и фотосессии**. Аудиторию привлекают современные технологии, полезные рекомендации и сильная визуальная составляющая.

### Запрос 2. Анализ «долгоиграющего» контента (просмотры после первой недели)
```sql
SELECT theme, views_1week, views_2week, (views_2week - views_1week) AS difference
FROM blog_post_stat
WHERE post_date BETWEEN '2026-09-01' AND '2026-09-30'
  AND views_2week > views_1week
  AND (views_2week - views_1week) > 2
ORDER BY difference DESC;
```
* **Вывод:** Высокую досматриваемость на второй неделе сохраняют посты про **AI и личные обзоры (например, обзор на тушь)**. Пользователям важен прикладной личный опыт, который приносит им пользу. Этот контент целесообразно переиспользовать на внешних площадках для привлечения новой аудитории.

### Запрос 3. Влияние визуального контента на просмотры
```sql
SELECT 
    CASE WHEN has_photo = 1 THEN 'С фотографией'
         ELSE 'Без фотографии'
    END AS photo_in_post,
    ROUND(AVG(views_1week), 2) AS avg_views_1week
FROM blog_post_stat 
WHERE post_date BETWEEN '2026-09-01' AND '2026-09-30'
GROUP BY photo_in_post;
```
* **Промежуточный вывод:** Посты без фото (5.67) набрали больше просмотров, чем с фото (3.86). Для проверки этого парадокса была проведена детальная разбивка с учетом тематики контента:
```sql
SELECT theme, 
    CASE WHEN has_photo = 1 THEN 'С фотографией'
         ELSE 'Без фотографии'
    END AS photo_in_post,
    ROUND(AVG(views_1week), 2) AS avg_views_1week
FROM blog_post_stat
WHERE post_date BETWEEN '2026-09-01' AND '2026-09-30'
GROUP BY theme, photo_in_post 
ORDER BY avg_views_1week DESC;
```
* **Итоговый вывод:** Само по себе наличие фото не определяет успех поста. Главный фактор — тематика. Технические и сложные посты (AI, софт) публиковались преимущественно без фото, но лидировали по просмотрам за счет ценности текста.

### Запрос 4. Влияние длины текста на дочитываемость
```sql
SELECT 
    CASE WHEN text_length <= 1000 THEN 'Маленький'
         WHEN text_length <= 2500 THEN 'Средний'
         ELSE 'Большой'
    END AS size_post, 
    ROUND(AVG(views_1week), 2) AS avg_views_1week
FROM blog_post_stat
WHERE post_date BETWEEN '2026-09-01' AND '2026-09-30'
GROUP BY size_post;
```
* **Вывод:** Длина текста не влияет на количество просмотров (маленькие — 4.5, средние — 3.55, большие — 4.5). Разница минимальна (в пределах 1 просмотра). Проверка с группировкой по темам подтвердила: если тема (IT, личный опыт, наука/психология) интересна читателю, он дочитывает лонгриды до конца. Главное ограничение по длине — лимиты самой платформы Telegram.

## Этап 2. Бизнес-рекомендации для контент-стратегии
1. **Оптимизация матрицы контента:** Сократить количество лайфстайл-постов на **50%**. Освободившиеся контентные слоты перераспределить в пользу высококонверсионных тем: **Психология/Наука (+20%)**, **IT-тематика (+15%)** и **Личный опыт (+15%)**.
2. **Снижение затрат на продакшн:** Снизить фокус на обязательное создание уникального визуала. Для технических постов фотографии не требуются, для остальных достаточно 1–2 релевантных изображений.
3. **Формат текста:** Снять ограничения на длину лонгридов для экспертных тем — объем знаков не снижает вовлеченность аудитории.

## Этап 3. Дата-инжиниринг и рефакторинг архитектуры БД

### Ограничения текущего анализа (Проблема)
Анализ проводился на выборке из 25 постов за один месяц. В процессе работы была обнаружена **архитектурная ошибка сбора данных**: еженедельные срезы хранились в одной плоской таблице. 

Посты, опубликованные в конце сентября, физически не успевали «прожить» 2–4 недели до момента выгрузки. Это приводило к искажению метрик динамики (в частности, `views_2week`) и могло повлечь неверные бизнес-выводы.

### Принятое решение
Перейти от плоской структуры к реляционной модели данных, начиная с октября 2026 года. Это разделит статичную информацию о публикациях и динамически изменяемые метрики. Временные интервалы срезов изменены с недель на дни (1, 7 и 14 дней), что полностью нивелирует фактор даты публикации контента.

### Новая DDL-архитектура базы данных (PostgreSQL)

```sql
-- Таблица 1. Справочник публикаций (Статичные данные)
CREATE TABLE post_stat_glob (
    post_id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    post_name VARCHAR(200),
    post_date DATE,
    post_time TIME,
    has_photo BOOLEAN, 
    text_length INTEGER,
    republish_count INTEGER, 
    pin_storefront BOOLEAN,
    vc_storefront BOOLEAN
);

-- Таблица 2. Журнал динамики метрик
CREATE TABLE views_din (
    views_id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    post_id INTEGER REFERENCES post_stat_glob(post_id),
    views_1day INTEGER,
    views_7days INTEGER,
    views_14days INTEGER,
    reaction_1day INTEGER,
    reaction_7days INTEGER,
    reaction_14days INTEGER
);
```

## Этап 4. План дальнейшей валидации
Сбор данных в новую структуру начат с октября 2026 года. Через 1 месяц запланирован повторный аналитический цикл для:
1. Валидации гипотезы о лидерстве IT-тематики и экспертного контента на большей выборке.
2. Оценки точности сбора данных без искажений «конца месяца» на основе новой таблицы динамики.
